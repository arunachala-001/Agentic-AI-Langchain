LangChain LCEL RAG — RunnablePassthrough & Retriever Quick Reference

1.  Overall LCEL chain

chain.invoke({“question”: “What is Pinecone?”})

Flow: Input dict → RunnablePassthrough.assign() → prompt_template → LLM
→ StrOutputParser → final answer

2.  RunnablePassthrough

Basic idea: RunnablePassthrough() means “pass the input through
unchanged”.

Example: input → RunnablePassthrough → same input

RunnablePassthrough.assign(…) is more useful in RAG: It preserves the
original input and adds new computed fields.

Example: Input: { “question”: “What is Pinecone?” }

After assign(context=…): { “question”: “What is Pinecone?”, “context”:
“retrieved document text…” }

Key idea: assign() = keep existing data + add new data.

3.  itemgetter(“question”)

from operator import itemgetter

itemgetter(“question”) is roughly equivalent to: lambda x: x[“question”]

So: {“question”: “What is Pinecone?”} → “What is Pinecone?”

4.  LCEL pipe operator |

A | B | C means: input → A → B → C

Conceptually: C(B(A(input)))

Therefore: itemgetter(“question”) | retriever | format_docs

means: 1. Extract question 2. Retrieve relevant documents 3. Convert
documents into a context string

5.  Retriever

Created with: retriever = vectorstore.as_retriever(search_kwargs={“k”:
3})

A retriever is a LangChain Runnable that converts: question → relevant
Documents

When: retriever.invoke(question)

it approximately does: question → query embedding → vector similarity
search → top 3 relevant documents → List[Document]

Important: k=3 means retrieve the top 3 documents.

6.  VectorStore vs Retriever

VectorStore: The interface to the vector database/search system.

Retriever: A standardized retrieval interface built from the vector
store.

Flow: PineconeVectorStore → as_retriever() → Retriever →
invoke(question) → Documents

The retriever can be directly composed in LCEL because it implements the
Runnable interface.

7.  Embeddings

OpenAIEmbeddings() converts text into numerical vectors.

Conceptually: “What is Pinecone?” → [0.02, -0.18, 0.73, …]

Documents are embedded when stored, and the query is embedded during
retrieval. Pinecone compares vectors to find semantically similar
documents.

8.  format_docs()

Your function: def format_docs(docs): return ”

“.join(doc.page_content for doc in docs)

It converts: List[Document] → one context string

Example: [ Document(page_content=“Pinecone is…”),
Document(page_content=“Vector databases are…”)] → “Pinecone is…

Vector databases are…”

9.  The key RAG expression

RunnablePassthrough.assign( context=itemgetter(“question”) | retriever |
format_docs )

Means:

Input dictionary → extract question → retrieve documents → format
documents → store result as “context” → preserve original “question”

Result: { “question”: “…”, “context”: “…” }

This is then passed to: prompt_template

because the prompt needs both: {question} {context}

10. Why not just use the retriever?

If you only do: question → retriever → format_docs

you end up with context but may lose the original question.

RunnablePassthrough.assign() solves this by keeping the original input
while adding the retrieved context.

11. Simple mental models

RunnablePassthrough: A → A

RunnablePassthrough.assign(): {A} → {A, B}

itemgetter(“question”): dict → question string

Retriever: question → relevant Documents

format_docs: Documents → context string

Prompt: {question, context} → formatted prompt

LLM: prompt → AIMessage

StrOutputParser: AIMessage → plain string

12. Full RAG flow

{ “question”: “What is Pinecone?” } ↓ RunnablePassthrough.assign() ↓ {
“question”: “What is Pinecone?”, “context”: “retrieved documents…” } ↓
ChatPromptTemplate ↓ LLM ↓ StrOutputParser ↓ Final answer

Most important takeaway: RunnablePassthrough.assign() preserves the
original input and adds computed values. The retriever performs semantic
search and returns relevant Documents. The | operator connects these
components into a data-processing pipeline.
